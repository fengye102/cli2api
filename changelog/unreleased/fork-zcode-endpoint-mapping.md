### English

- zcode: inference requests now follow the endpoint-mapping table the upstream publishes. The desktop client (3.7+) does not hardcode where it sends: it reads `GET /api/v1/agent/configs` and rewrites the request URL through `data.proxyEndpoint.mapping`, which is how the vendor moves traffic between planes without shipping a client — and it is what the documentation means by "编程套餐授权连接时端点由 ZCode 自动路由". A gateway that pins an endpoint starts failing the day it moves and has to wait for a release; this one follows within minutes. The rewrite is deliberately unable to cause a failure of its own: no snapshot, no matching entry, an unparseable table or a failed fetch all leave the URL untouched, the lookup itself is a pure table operation on the request path (no network, no retry), one background fetch runs per origin at a time with its own deadline, and a failed fetch keeps the previous table because not being able to read the table is not the same as the upstream having published an empty one. Matching follows the client's own rules: only `https` entries, key = lowercase host with the default port stated and the path minus its trailing slash, and the rewrite keeps the caller's query while dropping the target's. The table is capped at 256 entries, a bad entry is skipped rather than failing the whole thing, and a change is logged once so an operator can see the upstream having moved an endpoint. `ZCODE_DISABLE_ENDPOINT_MAPPING` stops both the fetch and the rewrite — the escape hatch if a published table ever misbehaves. Probed live: the upstream currently publishes one entry, `https://open.bigmodel.cn/api/anthropic/v1/messages` → `https://zcode.z.ai/api/v1/ultra/anthropic/v1/messages`, which is the coding-plan plane moving onto `zcode.z.ai`.

### 中文

- zcode：推理请求现在会跟随上游下发的端点映射表。桌面端 3.7+ 并不写死往哪发：它读 `GET /api/v1/agent/configs`，按响应里 `data.proxyEndpoint.mapping` 的 from→to 改写请求地址——上游就是靠这张表在不停发版的情况下把流量在计费平面之间搬，官方文档里「编程套餐授权连接时端点由 ZCode 自动路由」说的正是它。写死端点的网关在搬家那天开始全量失败，只能等发版；现在几分钟内就跟上了。改写本身被设计成**不可能自己造成故障**：没有快照、表里没这条、表解析不出来、拉取失败——一律原样放行；查表是请求路径上的纯内存操作（无网络、无重试）；同一 origin 同时只有一个后台拉取、带自己的超时；拉取失败保留旧表，因为「读不到表」和「上游说没有映射」不是一回事。匹配规则照客户端的口径：只认 `https` 条目，key 是 host 小写、缺省端口写明 443、path 去尾斜杠，改写保留调用方的 query、丢掉目标自带的 query。表上限 256 条，坏条目跳过而不拖垮整表，表发生变化时打一行日志，便于运维看到「上游搬了端点、我们跟上了」。`ZCODE_DISABLE_ENDPOINT_MAPPING` 会同时停掉拉取和改写——万一上游下发的表有问题，这是逃生口。实测：上游现在只下发一条，`https://open.bigmodel.cn/api/anthropic/v1/messages` → `https://zcode.z.ai/api/v1/ultra/anthropic/v1/messages`，也就是编码套餐平面正在往 `zcode.z.ai` 搬。
