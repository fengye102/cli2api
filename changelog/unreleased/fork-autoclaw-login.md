### English

- autoclaw: the channel can now log itself in, so an account no longer has to be created by importing the desktop client's file. The account plane has its own round and each build uses a different one: the domestic build texts a login code (`/userapi/v1/agent-send-code`, then `/userapi/v1/agent-login`), the overseas build runs the desktop client's OAuth redirect (`/userapi/overseasv1/{zai,google}-oauth-url` → browser → `/userapi/overseasv1/{provider}-oauth-login`). Both are interactive and the operator's browser is not on this machine, so nothing waits on a loopback socket: the console shows the authorize URL (or asks for the phone number) and the round is closed with a pasted value — the same paste box that was already there, now also carrying a phone number and an SMS code. Two details came from probing the live gateway rather than from documentation: the code has to go up as a JSON **number** (a string is refused with 400001) and `/agent-login/` now answers 307 to the slashless path, which a client that does not follow redirects has to handle (this one takes exactly one hop). The device id is derived from the account id, so the refresh token stays bound to the same device across restarts. The login capability is advertised for both builds, and a login that needs a second answer ("pending") no longer makes the console claim the account is ready.
- autoclaw-intl: `/overseasv1/zai-oauth-url` is fronted by an Aliyun captcha — verified live, a request without a proof answers code 631002 ("当前版本已停止服务"), and `/overseasv1/oauth-captcha-config` publishes the scene that would have to be solved (`scene_id=18vhnjxl prefix=sq51tr region=ga`). The bundled solver is scored as a bot on that scene, so the failure now explains itself with those parameters instead of echoing the misleading upstream message, and a `captcha` value passed from the console is forwarded for anyone who has a real proof. Domestic accounts are unaffected: the phone-code round has no captcha in front of it.

### 中文

- autoclaw：这个渠道现在可以自己登录了，账号不必再靠导入桌面端的文件才能建出来。账号面本来就有一套登录，两个版本用的不是同一套：国内版发手机验证码（`/userapi/v1/agent-send-code`，然后 `/userapi/v1/agent-login`），国际版走桌面端那个 OAuth 跳转（`/userapi/overseasv1/{zai,google}-oauth-url` → 浏览器 → `/userapi/overseasv1/{provider}-oauth-login`）。两条都是交互式的，而操作者的浏览器不在这台机器上，所以不会有任何东西去等本地回环端口：控制台把授权链接（或者「请填手机号」）显示出来，最后用一个粘贴值收尾——用的就是原来那个粘贴框，现在它也能收手机号和验证码。有两个细节是打真上游打出来的，不是文档里抄的：验证码必须以 JSON **数字**发送（字符串会被 400001 拒绝），以及 `/agent-login/` 现在会对不带斜杠的路径回 307，对不跟随重定向的客户端来说必须自己处理（这里只跳一次）。设备 id 由账号 id 派生，所以重启之后 refresh token 依然绑在同一台「设备」上。能力位对两个版本都开了；需要第二步答案的登录（pending）不会再让控制台谎称账号已就绪。
- autoclaw-intl：`/overseasv1/zai-oauth-url` 前面挂了 Aliyun 验证码——实测没有验证参数时回 code 631002（「当前版本已停止服务」），而 `/overseasv1/oauth-captcha-config` 会把要解的 scene 直接公布出来（`scene_id=18vhnjxl prefix=sq51tr region=ga`）。自带的求解器在那个 scene 上会被判定为机器人，所以现在失败信息会带上这些参数自己解释清楚，而不是照抄上游那句误导人的话；从控制台传进来的 `captcha` 会原样转发，供手上有真实验证参数的人使用。国内账号不受影响：手机验证码那一轮前面没有验证码。
