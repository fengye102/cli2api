### English

- The `zcode` channel now ships both services the desktop client signs in to, as two regions: `zai` (Z.ai — `api.z.ai`, the client's default) and `bigmodel` (BigModel — `open.bigmodel.cn`). New accounts default to `zai`. The two realms have different authorize hosts, callback schemes and API bases, so a credential is only ever sent to the service it was minted for.
- Add browser login for zcode accounts. Z.ai uses the sign-in the ZCode CLI runs: the console asks the plan gateway to mint a flow (`POST /oauth/cli/init`, authenticated by a 32-byte poll token minted for that round), opens the returned authorize URL, and then polls (`GET /oauth/cli/poll/<flow>`, reporting the remaining minutes rather than a wall clock so the message reads the same in any container timezone) until the gateway answers ready — at which point the credential (ZCode JWT, provider access token, identity) is stored and the console reports the account ready. Nothing about that round needs the operator's machine: the authorize URL redirects back to `zcode.z.ai`, so neither a custom scheme nor a local port is involved and whatever desktop app registered `zcode://` (an account manager, say) has nothing to swallow. When the gateway cannot mint a flow the console falls back to the paste round trip: it opens the region's authorize page and accepts the pasted callback URL, which is exchanged at `https://zcode.z.ai/api/v1/oauth/token`, with Z.ai's returned access token then exchanged at `https://api.z.ai/api/auth/z/login` for the ZCode JWT the chat path uses. BigModel keeps that paste flow only (`zcode://oauth/callback`), and its token response already carries the JWT. Account identity (email, user id) is filled best-effort from the realm's userinfo endpoint.
- The paste round is bound to a 32-byte `state` minted per start and expires after 15 minutes, so a callback link from an earlier round cannot complete a newer one; the pasted URL is validated (scheme, the callback hosts of that region, `code`/`authCode`, provider `error`) before any exchange happens, a paste is refused outright while a Z.ai CLI round is running, and a rejected exchange leaves the account untouched. Pasting an API key is exposed as the PAT login method alongside it.

### 中文

- `zcode` 渠道现在同时提供官方桌面客户端登录的两个服务，各占一个区域：`zai`（Z.ai——`api.z.ai`，客户端默认）与 `bigmodel`（BigModel——`open.bigmodel.cn`）。新建账号默认 `zai`。两个服务的授权域名、回调协议与 API 地址都不同，因此凭证只会被发到它所属的那个服务。
- 新增 zcode 浏览器授权登录。Z.ai 走的是 ZCode CLI 那套登录：控制台先让计划网关开一个登录流程（`POST /oauth/cli/init`，用本轮现生成的 32 字节 poll token 鉴权），打开返回的授权链接，然后轮询（`GET /oauth/cli/poll/<flow>`，提示剩余分钟数而不是具体时刻，这样容器时区是 UTC 也不会误导）直到网关回 ready——此时凭证（ZCode JWT、服务方 access token、身份信息）写入账号，控制台显示登录完成。这一轮完全不需要碰用户机器：授权链接的回调指向 `zcode.z.ai` 自己，既没有自定义协议也没有本机端口，所以机器上注册了 `zcode://` 的桌面软件（比如账号管理器）没有东西可抢。若网关开不出流程，控制台退回「粘贴回调」方式：打开该区域的授权页，接受用户粘回的回调链接，去 `https://zcode.z.ai/api/v1/oauth/token` 换取 token；Z.ai 还会用换到的 access token 再到 `https://api.z.ai/api/auth/z/login` 换取对话路径用的 ZCode JWT。BigModel 区域只有粘贴这一种方式（`zcode://oauth/callback`），其 token 响应里直接带 JWT。账号身份（邮箱、用户 ID）尽力从对应区域的 userinfo 接口补齐。
- 粘贴方式每轮新生成 32 字节 `state` 且 15 分钟后过期，因此上一轮的回调链接无法完成新一轮登录；粘贴的链接在真正换取 token 之前会先校验（协议、该区域允许的回调 host、`code`/`authCode`、上游 `error` 参数）；Z.ai 的 CLI 登录进行中会直接拒绝粘贴；换取失败不会污染账号。同时把「粘贴 API Key」作为 PAT 登录方式一起开放。
