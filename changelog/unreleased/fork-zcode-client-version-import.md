### English

- zcode: the client build this gateway reports now follows the release ZCode is on (3.16.3) instead of a pinned 3.14.3, and `ZCODE_APP_VERSION` pins it back without a rebuild if the plan gateway ever turns a newer build away. ZCode moved its own sign-in twice and the import path now matches: 3.15 keeps no coding plan key in `credentials.json` and uses the one in `config.json`'s provider table (magpie#2130), and that table usually holds other agents' sections too — magpie's own gateway entry among them — so the section naming a ZCode site is imported rather than the first `apiKey` found, which also made the choice random from one import to the next. A ZCode `credentials.json` can be imported as-is once the operator supplies the seed the client sealed it with (`ZCODE_CREDENTIAL_SECRET`, or `ZCODE_CREDENTIAL_SEED` holding the whole `zcode-credential-fallback:<platform>:<home>:<user>` string): every `enc:v1:` value opens and the file is read whole, session and identity included. 3.16 files keep neither the key nor a way to decrypt without that seed, and hold only a `project-key-location` — that case now says so instead of reporting a missing credential.

### 中文

- zcode：上报的客户端版本不再死钉 3.14.3，改为跟随 ZCode 当前发版（3.16.3）；若上游哪天拒绝新版本，用 `ZCODE_APP_VERSION` 就能钉回旧版本，不必重新构建镜像。ZCode 两次搬家都跟上了：3.15 不再把 coding plan 的 key 放在 `credentials.json`，而是放在 `config.json` 的 provider 表里（magpie#2130），而那张表通常还摆着别的 agent（包括 magpie 自己的网关条目），所以现在优先取「baseURL 指向 z.ai / bigmodel 或 id 含 zcode」的那一段，而不是「随便第一个 apiKey」——后者不但会导错别家的 key，而且 Go 的 map 顺序让每次导入选到的都不同。ZCode 自己的 `credentials.json` 现在可以整文件直接导入，只要运维提供客户端当时用的种子（`ZCODE_CREDENTIAL_SECRET`，或把整条 `zcode-credential-fallback:<platform>:<home>:<user>` 放进 `ZCODE_CREDENTIAL_SEED`）：所有 `enc:v1:` 值会被解开，会话和身份一起读出来。3.16 的文件两者都不留、只留一个 `project-key-location`，这种情况现在会直接说明，而不是含糊地报「缺少凭据」。
