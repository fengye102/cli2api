# 首字节感知选号（lowest-ttfb）落地方案

> 状态：**已实现**（`feat(executor): route on first-byte latency instead of racing two accounts`）
> 取代：[`慢请求竞速对冲落地方案.md`](./慢请求竞速对冲落地方案.md)（因计费前提不成立而作废）

## 1. 问题

我们对逆向通道（raccoon / zcode / autoclaw）的首字节耗时抖动没有感知。同一个公开模型，
池里 A 账号 300ms 出字，B 账号要 10 秒；而调度器是**轮询**，于是每两次请求就有一次
砸在 B 上，用户看到的就是「卡住」。

现有的 failover 解决不了：请求并没有失败，它只是慢。B 最终也会返回 200，failover 无从触发。

## 2. 为什么不是「对冲」（原方案）

对冲（首字节迟到就并发打第二个账号）用户体验最好，但**代价是双倍上游调用**。
2026-11-02 的实测（详见作废文档第 10 节）显示：raccoon 与 autoclaw 在请求被切断后
余额仍在掉（autoclaw 单条被切断的请求扣了 68 分，而一条正常完成的请求只扣 1 分），
只有 zcode 无法定论。也就是说对冲很可能**用双倍积分换几秒**。

所以本方案的硬约束是：**每条请求只发一次**。只改变「发给谁」，不改变「发几次」。

## 3. 设计

### 3.1 数据：每个账号一个首字节 EWMA

- 采样点在**拿到响应头**的那一刻（`executor/chat.go` 两条成功路径各调一次
  `observeTTFB`），不是流结束时。流时长由用户 prompt 决定，跟账号质量无关。
- `EWMA` 平滑系数 `α = 0.3`：约 3 次请求收敛。够快能立刻压下一个变慢的账号，
  够慢让一次侥幸的快样本无法把一个账号顶上去。
- **只统计成功的尝试**。超时/断流已经走了冷却路径，再折进平均值等于对同一次失败罚两遍。
- 读数下限 `20ms`：更小的值不可能是真的首字节（本地失败/空响应），不予采信。

### 3.2 抗抖动：winsorize 而不是直接平均

一个健康账号偶尔卡一次 9 秒，如果直接进 EWMA，估计值会从 300ms 冲到 2910ms，
把一个好账号踢出候选——这比不优化更糟。

所以样本在**超过当前估计 3 倍**时被削到 3 倍：300ms 的账号遇到一次 9 秒，按 900ms 计，
EWMA 只到 480ms。而**持续**变慢仍然会爬升，因为天花板跟着估计值一起上移：
连续 9 秒 → 900 → 2700 → 8100 …，几轮之后账号照样被降级。

这个区分很重要：它区分的是「偶发」和「坏了」。

### 3.3 选号：取 band 再轮询，而不是取单一最优

如果只挑最快的账号，整条路由会全压到它身上，把它打成饱和，然后所有人一起变慢。

所以策略是**先筛出一个带**：得分不超过 `最优 × 1.25 + 150ms` 的账号全部保留，
再在带内沿用原有的轮询游标（`successorIndex`）。

- 300ms 与 400ms 的两个账号：上限 = 400 × 1.25 + 150 = 650，两个都在带里 → 继续分担流量。
- 300ms 与 9000ms：上限 = 525 → 慢的那个出局，直到它交出新的快样本。

### 3.4 冷启动：必须等价于轮询

没有样本的账号按**先验 1200ms** 计分。先验取「带内已有样本的中位数」，
全池无样本时取常数 1200ms。

- 全池无样本 → 所有账号同分 → 带 = 全体 → 与轮询完全一致（有单测锁定）。
  这意味着**开启这个策略本身不会改变任何流量分布**，只有证据出现后才开始分化。
- 新账号 → 1200ms，介于「健康（300ms）」与「明显卡顿（9s）」之间：它会被试到
  （否则永远采不到样本），但不会顶掉一个稳定 300ms 的账号。
- 样本 `10 分钟`后失效 → 退回先验。一个十分钟前很快、现在卡死的账号，
  不能靠旧功劳一直霸占路由；失效后它会重新被试用，恢复也会被重新认可。

### 3.5 不持久化

窗口是进程内内存，重启即清空。理由：① 首字节主要由上游当下的状态决定，
昨天的样本没有参考价值；② 避免给 `Pool` 加一条写库路径；③ 冷启动等价于轮询，
所以清空本身是安全状态。

## 5. 配置与灰度

- 位置：**系统 → 账号调度策略**，或 `PATCH /api/system/settings {"routing_strategy":"lowest-ttfb"}`。
- 默认仍是 `round-robin`：**不主动切换就完全没有行为变化**。
- 建议灰度顺序：
  1. 先在单渠道池（raccoon 或 autoclaw）上切，观察 24h；
  2. 看 `request_logs.ttfb_ms` 的 p95 与各账号请求数分布；
  3. 全池切换。
- 回滚：改回 `round-robin` 即可，样本窗口不影响其它策略（`SetRoutingStrategy` 保留样本，
  所以来回切换不会有额外损失）。

## 6. 单测（已通过）

1. `TestLowestTTFBColdPoolMatchesRoundRobin` — 冷池逐条与 round-robin 序列完全一致；
2. `TestLowestTTFBSkipsStalledAccount` — 卡顿账号 12 次选号中一次都不出现；
3. `TestLowestTTFBSpreadsAcrossEquallyFastAccounts` — 两个同样快的账号都保有份额；
4. `TestLowestTTFBForgivesExpiredSample` — 样本过期后账号重新进入候选；
5. `TestObserveTTFBRejectsNoise` — 下限读数与空 ID 不进入窗口；
6. `TestObserveTTFBSmoothsSingleOutlier` — 一次 9s 抖动不驱逐账号，但连续 9s 会降级；
7. `TestSetRoutingStrategyKeepsTTFBSamples` — 切策略不丢窗口；
8. `TestNormalizeRoutingStrategyLowestTTFB` — 大小写/空白归一化，未知值回落 round-robin。

另有 API 层 `TestSystemSettingsRoutePersistsLowestTTFBRoutingStrategy`：`PATCH` 能落库、
能实时生效、能被读回。

## 7. 验收标准

1. **不切换则行为不变**：跑 `round-robin` 时选号序列与改动前逐条相同（现有测试全绿）；
2. 切换后 24h：`request_logs.ttfb_ms` 的 p95 下降（目标 ≥30%），
   同时各账号请求数**不出现单点集中**（band 轮询生效）；
3. `request_attempts` 无新增失败类型，冷却账号数不上升（本策略只改选号，不碰失败处理）；
4. 上游调用次数**不变**（这是与对冲的本质区别，可直接用上游账单核对）。

## 8. 风险与已知局限

| 风险 | 现状 |
|---|---|
| 全池都慢时无收益 | 明确局限：策略只在候选集内排序，不能凭空创造快账号 |
| 冷启动前几条请求按旧方式分布 | 可接受：等价于轮询，且 3 条请求即收敛 |
| 首字节快但吐字慢的账号被高估 | 明确局限：本方案只看首字节（用户感知的「卡住」主要发生在这里）；吐字速度需要另一套指标 |
| 同账号多模型混用一个估计 | 明确局限：当前按账号聚合，不按「账号×模型」；模型间首字节差异大的渠道（如 autoclaw 的 flash/pro）后续可细化为二维键 |
| 进程重启丢窗口 | 已论证安全（冷启动=轮询） |
